# 目标视频与当前 RGB 包的性能、能力差距复核（2026-11-15）

结论：完整 RGB 数据链路与基础视线跟随已经建立，但在窄视场、小目标和复杂背景下，距离参考视频展示的效果仍有明显差距。本次增补测试未通过，不能用之前友好场景的约98.6%可信选定状态比例概括当前能力。不能给出“已达到视频百分之多少”：视频没有独立标注、原始遥测和时延记录。

## 性能及能力差距

| 项目 | 参考视频可见信息 | 当前证据与差距 |
|---|---|---|
| 画面节奏 | 编码30FPS，算法速率未知 | 当前UE→ROS完整采集段平均约26.1–28.8FPS；网页默认5FPS，显示节奏明显较低 |
| 发现/检测速度 | 无法从录像测量 | 本次UE并行渲染、记录及评估负载下，全图D-FINE链路1.90–2.53FPS；不能把20多Hz的lost状态发布算作跟踪成功 |
| 视场/目标尺度 | 部分HUD为3.3°、EO22.3x | 默认固定90°；实际已验证90↔60°变焦闭环，45°仅为配置允许下限，3.3°未经实现和验收 |
| 小目标 | 字幕宣称16×16px | 新增区约15×9px无人机、28×27px车辆，给定初框后也未持续锁定；需要先修复这一能力边界 |
| 背景变化 | 天空→树林→水面等片段 | 有相机运动补偿、颜色可信度和局部光流，但新增低对比/强纹理区域暴露出可信测量持续性不足 |
| 遮挡/干扰 | 有道路环境，不能量化完整遮挡恢复 | 新增同类干扰和三档顶棚，当前试验在静止阶段已失锁，尚不能宣称遮挡恢复合格 |
| 云台/闭环 | 可见视角随目标变化 | 当前云台有角度/速度/加速度/80ms执行延迟模型；窄视场下的预测视线控制未验证 |
| 空间跟随 | 不能证明距离、三维定位或目标驱动航线 | PX4默认任务航线和图像视线闭环已有验收；目标驱动的飞行追随、真实距离及空中三维定位仍未验收 |
| 多模态 | 有灰度及伪彩片段 | 当前明确是RGB；没有真实红外传感器、EO/IR融合和热成像跟踪能力 |

若3.3° HUD可信，同距离、同目标、理想针孔条件下，90°画面的目标线性尺寸比3.3°约小34.7倍；60°约小20.0倍，45°约小14.4倍。分辨率、距离和镜头畸变不同会影响实际比较，不能把这些比例称为检出率差距。960宽图像输入640宽全图检测时，16px目标还会缩到约10.7个模型输入像素。

此前实际选定目标PX4试验 `reports/ue_geometry_stage5_20261115/px4_live_10_installed/capture_summary.json`：采集→ROS P50/P95=76.8/85.4ms，采集→控制=222.1/279.9ms，采集→执行器=335.5/398.9ms，28.2FPS。另一组执行器中位数395.6ms，说明负载会影响结果。它们是已成功跟随场景的实测；本次失败场景没有足够持续的有效控制样本，不能混作同一统计。

举例而非视频实测：902宽、3.3°针孔相机，目标角速度4°/s、未补偿延迟335.5ms时，理想投影滞后约367px；90°时约10.6px。长焦会同时放大像素目标和闭环误差，直接减小FOV并不能保证达到视频效果。屏幕示例2→8秒航向变化约7.37°、俯仰约16.94°，说明巨大的画面背景运动不等同于极高真实角速度；不能据此反推目标m/s。

四组均成功提交初框，但在启动目标运动前最后2秒的可信当前测量比例已为0；之后20秒没有恢复正确锁定。不能由此得出“连2m/s都跟不上”的速度结论，也不能把无有效轨迹时ID切换0解释为优秀。遮挡场景同样不能用来估计恢复时间上限。无人机约15×9px的结果接近参考片段宣称的小目标尺度，但本次没有达到稳定跟随。

链路与覆盖核验：每组日志中D-FINE推理、配置NMS、外部BoT-SORT、时间分类一致性计数一致；Fusion下均有camera_motion、visual_flow、候选过滤/去重、ROI颜色、特征跟踪和仲裁执行记录，保留SAR→XD桥及网页。三组车辆的选定目标光流调用分别14/12/13次，但空中小目标为0，诊断为not_eligible。代码要求上一帧observed、时间连续、无待确认身份，才运行该独立LK分支；这组未建立可信跟踪，未跨过资格门限。因此不能声称每个场景的全部分支均成功激活。需进一步区分初始ROI外观质量不足和首帧立即失效，不能直接删除可信度条件来掩盖这一问题。失败时输出lost而没有靠预测框冒充有效实测。调用计数不代表每帧均有效，失锁后分支会按可信度条件拒绝或停止更新。

KCF核验：正式 `sar_yolo_smart_tracker` 启动包装器会为本机D-FINE解释器加载批准的contrib环境；该路径实测OpenCV4.10.0，KCF/CSRT可用。配置为KCF、`allow_template_fallback:false`。单独直接启动模型解释器可导入另一个无contrib的cv2，这不是正式链路的运行环境。新自动工具加入同等环境预检，缺KCF/CSRT时拒绝启动测评。

失败日志示例：ground_2mps_h60 的fusion_evidence中，特征分支曾accepted=true、score≈0.72、appearance_similarity≈0.94，但颜色score≈0.03且未接受，目标局部光流不满足条件，检测没有形成可接管的选定轨迹，仲裁返回no_trusted_visual_observation，随后identity_memory_waiting。可见“各分支执行了”不等于“融合后能锁住”。该结论来自单组日志样本，后续还需按尺度/纹理分桶分析，不能归因于单一门限。

所有四组保存28秒录像窗口的实际RGB bag及已记录帧的标定/姿态清单、初末截图、状态、trace、云台反馈、独立投影日志。另发现记录通道也有性能差距：bag实际有效帧率分别约28.09、25.55、12.71、24.28FPS，空中场景明显低于实时发布频率；保留每一记录帧的精确K/TF不代表录像无掉帧。共2533个记录RGB帧均有匹配K/TF，但应根据recording_coverage.json检查相对桥发布的留存率。实时评分使用独立状态和投影日志，没有把不完整bag当作全帧GT或用其回放结果冒充实时性能。相对同一捕获时间区间内桥已发布帧，空中bag留存率仅45.5%。记录丢帧原因尚未定位，不能只凭这些数据归因于磁盘或压缩。原始数据在 `validated/`，汇总 `stress_analysis.json`。前期射线接口返回值处理错误的批次已标记无效并重测，不计入这张表；另一个近距离场景未取得合法初框，只算初始化失败。其余12/20m/s、160m等预设尚未执行，不宣称通过。

## 建议升级顺序与下一次验收标准

1. 先解决静止小目标选定后的持续性：重放本轮失败片段，逐帧核对KCF/目标局部LK/颜色/检测接管的证据和误差；比较NanoTrack、OSTrack候选时保持同一数据、云台和仲裁标准，不能只放宽门限造成假锁。
2. 同时定位记录通道的掉帧，明确来源校验、K/TF配对和完整帧留存是不同验收项。在当前UE并行负载下评估D-FINE加速（固定尺寸FP16/合适导出后端、GPU竞争及延迟分位数），并保持局部跟踪独立调度。提高采集帧率不能单独解决约0.4–0.5秒模型处理及证据不足。
3. 固定90°下先通过静止、2/6m/s、同类干扰和可控遮挡，再逐步60°、45°，按实际内参和测量年龄验证预测视线控制、角速度前馈与失锁保护。3.3°应作为后续专门验收，不能只改配置上下限。
4. 独立补充审核后的UE/真实俯拍标注与负样本，测自动检出和分类混淆；本次给定ROI的指标不能替代它。静止小目标和复杂背景通过后，再在同场景加入PX4路线/机动；目标驱动飞行追随与距离/三维位置另行验证，空中目标不套地面约束。
5. 真红外传感器及EO/IR融合继续后置；RGB灰度或伪彩处理不作为红外验收。

分阶段的建议门槛：正确可信可见状态比例≥90%、中心归一化误差P95≤0.10、可见阶段最长正确测量间隔≤0.5秒、ID切换0；报告完整遮挡时长与重捕时间，并单列误锁率、各类自动检出及采集→执行器P95。只有先建立持续锁定，才有意义测更高速度边界。

复现与部署工具：[功能包操作说明](ue_stress_benchmark.md)。本次没有修改权重、检测跟踪算法或放宽验收标准，也没有上传Gitee。
